# Published-post availability and reposts

Run migration `d8e4b2c61709` when deploying this version, then update both web and worker from `origin/main` through the normal user-managed deployment workflow.

The worker checks confirmed live publications every six hours by default, including posts older than 90 days. Checks run in a separate scheduler job, independently of analytics, automatic-post generation, and publishing pauses. Configure `POST_AVAILABILITY_ENABLED`, `POST_AVAILABILITY_INTERVAL_HOURS` (1–168), and `POST_AVAILABILITY_BATCH_SIZE` (1–100, default 20). A backlog is handled in bounded batches; configured intervals are a target, not a real-time deletion notification.

The post workspace and overview show **Available on platform**, **Unavailable on platform**, **Couldn't verify**, or **Not checked yet**, along with the last check. The workspace also shows the last successful observation and check history. Unavailable and unverifiable publications appear in **Needs attention**. **Check availability now** makes a fresh read. Availability is separate from the `published` lifecycle status: original publication times, cadence usage, remote IDs, requests, content and audit records remain intact. Simulations and unconfirmed TikTok inbox deliveries are not monitored as public posts.

**Unavailable** means the official API no longer returns the post, or reports it is no longer published. It does not prove whether someone deleted it, made it private, or changed access. Expired credentials, explicit permission rejections, rate limits, transport errors and malformed responses produce **Couldn't verify**, never a deletion claim. No browser scraping or public-URL status heuristic is used. A successful lookup confirms the connected account can retrieve the object; it does not certify visibility to every audience.

For an unavailable publication, open the original on the platform and tick the confirmation that it is no longer available, then select **Prepare repost for review**. The app checks again before creating a new draft with the saved media, caption, fact version, and a new delivery key. Repeated clicks open the same draft; deleting that draft allows another attempt with the earlier record retained. Failed replacement attempts use the existing retry workflow, including its protections for uncertain delivery. No removal automatically creates or publishes a repost.

Repost drafts run the ordinary checks and require human approval, even if the original came from an automated campaign. Only explicitly linked unavailable originals are exempted from duplicate detection; unrelated similar posts still block. Every gate, including the final delivery gate, reads the original again. An original that returns or cannot be verified blocks delivery, even outside the normal duplicate window. Cadence caps and the original-account requirement still apply.

## Official read contracts checked 2026-11-16

- Instagram and Facebook use the original object ID and the minimal `id` field. Meta's [error handling guide](https://developers.facebook.com/docs/graph-api/guides/error-handling) distinguishes authentication, permissions and rate limits. Object-level code 100/subcode 33 is treated as inaccessible only after the original account can still be read; the UI explicitly retains the permissions ambiguity. It is never labeled a confirmed deletion.
- LinkedIn uses `GET /rest/posts/{encodedUrn}` with the configured version and Rest.li headers. The [Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-09) supports retrieval; its [error guide](https://learn.microsoft.com/en-us/linkedin/shared/api-guide/concepts/error-handling) notes that 404 can also describe inaccessible resources.
- X uses [Get Post by ID](https://docs.x.com/x-api/posts/get-post-by-id). Both HTTP not-found responses and a successful response containing a matching `resource-not-found` problem are recognized. Requests remain read-only; this feature does not invoke the X repost/retweet API.
- Pinterest uses `GET /v5/pins/{pin_id}` from its [official OpenAPI description](https://github.com/pinterest/api-description/blob/main/v5/openapi.yaml), with `pins:read`. Pins remain subject to the existing real Drive media requirement when reposted.
- TikTok uses the actual public video IDs, not the inbox publication ID. Those IDs are retained when manual publication is reconciled, or recovered through publication status. The [Video Query API](https://developers.tiktok.com/docs/en/tiktok-api-v2-video-query) then checks them using `video.list`. New connections request that scope when monitoring or analytics is enabled; existing connections without it must reconnect. Historical inbox status alone is never used as evidence that a video remains available.

Tests use mocked official responses and synthetic media. They are not live platform certification. No production migration, restart, public post or repost is performed by implementing this feature.
