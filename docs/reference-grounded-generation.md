# Product references in social content

The pipeline now sends actual product images to the generator. Website text and uploaded-media summaries still help plan the story, but they are not substitutes for visual inputs. This applies to live generated images and every generated video clip, including later clips and replacements.

The source order is current owner corrections, the versioned AI Builder drawing guide, compatible company images, then creative direction. The Builder snapshot and its source hashes are documented in [Builder visual guidance](builder-visual-guidance.md). Caption facts remain separate and immutable; reference images do not authorize new product claims.

`social/rendering_guidelines.py` records the current rendering policy. It requires straight, connected aluminum profiles, the supported roof and support arrangement, selected accessories only, and consistent geometry across a scene. Hanger rods stay above the canopy and connect the outer fascia to higher wall anchors. Wood Look remains an aluminum finish. Fixed louvers stay fixed. Camera moves should keep critical connections visible and avoid inventing the hidden side of a structure.

## How references reach the generator

1. The planner and prompt writer receive the rendering policy and Builder rules.
2. Before each live generation, the worker finds Public company images across the asset library, including Google Drive imports. Selected references come first, then product matches from tags, filenames and existing visual summaries; matching Drive imports have preference. Logos, expired/restricted media, unpermitted customer material and unsolicited earlier AI generations are excluded. Up to six library candidates are inspected per scene. Good product-family tags improve retrieval in large, unclassified libraries.
3. The selector also receives product images from the reviewed, fixed URLs in `config/website-product-references.yaml`. Only HTTPS images on `tudelu.com/system4/` are fetched, without redirects, with size and image bounds. Downloaded bytes and checksums are retained. Website imagery is recorded as having an unverified creation method, not mislabeled as real company photography or a known AI model. Website errors do not prevent using a suitable library photo. No suitable drive-through photo was identified on the current website page, so that family needs a library reference.
4. OpenAI inspects the actual candidate pixels against the selected Builder product profile, current owner corrections and scene request. It chooses a compatible image and writes a short description of the configuration and a reference-aware generation prompt. It prefers a real company photo when equally suitable. A conflicting support, roof or selected option is a reason to choose another image or stop, not something a motion prompt is expected to repair.
5. The chosen original bytes are uploaded to Runway. Images use `referenceImages`; every generated video clip uses `promptImage` with the image-to-video endpoint. Later storyboard clips no longer discard their references. Video motion preserves the starting scene's product; new architecture and unobserved viewpoints are not invented to satisfy a camera instruction. This follows Runway's [image-to-video inputs](https://docs.dev.runwayml.com/api/) and [prompting guidance](https://help.runwayml.com/hc/en-us/articles/48324313115155-Image-to-Video-Prompting-Guide).
6. The reference, checksum, source, rule versions, selection explanation and exact submitted prompt are committed before generation. Resuming an unchanged selection reuses it. Changed clip instructions trigger a fresh selection; permissions and bytes are checked again before submission. Library references join output ancestry so later permission changes invalidate dependent approval. Website source bytes remain linked through the recorded reference plan.
7. Final visual review receives the original comparison images separately from the generated frames, with distinct image numbering. It still checks the actual result against Builder rules. The workspace and In progress show each clip's product reference and source link. Human review and all publication checks remain active.

If no compatible reference is available, the job explains the missing product/configuration and stops before buying a generation. It does not silently revert to text-only product generation. Add or tag a clear Public photo from Drive/the library, then resume. A photo whose critical geometry is unclear may need another view. Reference selection and final review are model judgments; this workflow cannot guarantee geometrically perfect video or certify unobserved frames.

Offline fixtures make no reference-selection or generation calls. Existing real-media uploads retain their own-media workflow. Existing video edits retain their source video and Builder constraints. Already-running tasks keep their recorded inputs; completed clips are not automatically regenerated or republished. A replacement affects the requested clip, so other flagged clips still need correction.

## Release and verification

No database migration is required: evidence uses existing job/asset JSON fields. Deploy updated web and worker from GitHub `main` through the user-managed release process. No production deployment or paid media generation was performed while implementing this change.

Tests cover actual image payloads for later clips, source selection and caching, changed permissions, missing and conflicting references, website errors/redirects, output ancestry, replacement/resume behavior, and separate comparison-image numbering in final review. Provider calls use mocks; public website images were retrieved and visually inspected separately.
